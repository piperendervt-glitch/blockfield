## 本プロジェクトの目的

生態系シミュレーションは目的ではなく実験装置である。最終的な
目的は、行動主体である個体の処理負荷を下げること（応用先:
見守り・巡回AI、フィジカルAI）。

したがって各Demoの真の評価軸は「生態系がリアルか」ではなく
「個体が持つべき状態と計算がどれだけ減ったか」である。
Demo 8 第1段で狼の視界内探索（O(N²)）が削除され、個体数に
依らない O(1) になったことが、その第一の成果。

場の追加・削除の判定基準:
- 進化的アルゴリズムで重みが0に収束した場は削除候補
- ただし重みの絶対値では判断しない（場ごとに値のレンジが違う）。
  実効寄与 = 重み × その場の勾配の典型的大きさ で比較する
- 最終判定はアブレーション（実際に削除して48シードで生存率・
  行動性能が有意に悪化しないか）
- 削除の動機は負荷削減より探索空間の縮小である可能性が高い。
  場の更新コストは個体数に依存しないため、**場化した対象が多いほど
  有利で、差は個体数とともに広がる**（場を増やした方が個体負荷は下がりうる）
  - Demo 8.5（植物の場化）の実測: 交差点は存在せず、測定した全個体数
    （11〜362）で場方式が速い。移行前は動物に加えて植物 Entity を
    100〜300体抱えるため、動物が少ない領域でも総エンティティ数では
    場方式が有利になる。差は個体数とともに広がる
    （22体で ‑16ms、362体で ‑39ms / 1000ティック）
  - ただし**場化しただけでは速くならない**。個体ループを全セル走査に
    置き換えた直後は +19% 遅くなり、ループの統合と対象セルの索引化で
    ようやく基準を下回った。場化は「個体数への依存を切る」ことであって
    「無条件に速くなる」ことではない
- 測るべき指標は「場の枚数」ではなく「1個体が1ティックで読む
  場の数」と「個体が持つ状態の数」

## 押し付け候補リスト（個体の計算を場へ移す候補）

1. 植物の場化（Demo 8.5）— 植物を Entity でなく植生場の値そのもの
   にする。エンティティ数が桁で減る
2. 未訪問度の場（Demo 6 と対）— 時間で増加し通過でリセット。
   個体は高い方へ動くだけで巡回が成立。巡回AIに直結
3. タスク場と予約（Demo 7）— やるべき場所に値が立ち、向かう個体が
   予約（負値）を書く。個体間通信なしの役割分担
4. 通行コスト場（踏み固めと統合）— 高低差計算を場読みに置換
5. 繁殖をコロニー場に（第4段の延長）— 隣接走査を場の閾値判定に
6. 時間管理の部分的な場化（食欲の場化で実験）— 完全な移管は
   個体差を消すため、進行速度の環境依存化など部分形を探る

## 実装済みの横断資産

以降のDemoが前提にできる、確立済みの仕組みと制約。

### 仕組み
- 決定論: f(初期シード, イベントログ)。World.Replay で
  任意のイベント列から同一 ContentHash に到達可能
  （Demo 6 の PC 側バッチが再検討される場合はこの機構をそのまま
  使える。現時点では Quest 単体で完結）
- 場（Field）: typed array 相当の float グリッド。
  植生場が拡散・減衰・書き込みで稼働中（τ小の速い層）
- 出所属性: Terrain / Player / Ecology / Reality の4値。
  TrySetBlockEcology が Player セルへの生態系側書き込みを
  API レベルで拒否（固定レイヤー原則）
- ボクセルレイキャスト: DDA（Amanatides & Woo）＋
  Predicate 遮蔽オーバーロード。エンティティと地形を
  統一的に狙える（将来の木・構造物にも適用可）
- チャンク限定再メッシュ: DirtyChunks 通知 → 該当チャンクのみ
  再生成（実測 0〜5ms）
- 表示と真実の分離: シムは 1Hz の決定論、表示は補間と仮表示。
  World の状態を表示側は決して変更しない

### 制約・知見（実機で観測済み）
- MR合成: α<1 の描画はパススルー（現実映像）と合成される。
  半透明表現は原則使わず、スケール・ワイヤーフレーム・明度で代替
- オクルージョン: 環境深度の取得だけでは不足。ARShaderOcclusion＋
  XR_HARD_OCCLUSION 対応シェーダーが必須
- HDR は無効必須（B10G11R11 はアルファを持たずパススルー合成が破綻）
- Passthrough は Android API 32 以上を要求
- 性能余裕: 8万ボクセル＠72FPS、地形生成 20ms、
  再メッシュ 0〜5ms（部屋スケール化の余地は大きい）

### 運用
- 実機テスト: 手順を事前固定し、装着中は指示・質問・生存報告を
  一切しない。ログ捕捉はスクリプト（capture_session.ps1）で行い、
  Claude Code はセッション後に一度だけ読む
- モデル使い分け: 設計判断・難所のデバッグは上位モデル、
  ビルド/デプロイ/文書記入/コミット等の定型は下位モデル

## Demo 4.5: Room Terrain — 部屋が箱庭になる（新規）
- シーンモデル取得: ARMeshManager（グローバルメッシュ）＋
  ARPlaneManager（ラベル付き平面）
- 多層ハイトマップ化: XZグリッド各セルへ上から下にレイキャスト、
  複数ヒット（机上面→床面）を記録し、各ヒット面に薄い地形
  （1〜4層の起伏）を雪が積もるように載せる
- 壁の Boundary 化: 壁平面を通行不可セルとして VoxelGrid に
  ラスタライズ。既存の徘徊AIが自然に壁を避ける
- 平面ラベル→バイオーム対応: 床=平原、机上=丘陵、棚上=山岳
  （vision の「初回観測」の地形版）
- 分散生成: 生成1〜3分許容、フレーム分散
- Go条件案: 床と机の両方に地形が積もる / 動物が壁を越えない /
  机上と床で異なるバイオーム / 生成3分以内
- 配置理由: Demo 3 の生態系をジオラマで安定させてから空間を
  広げる。Demo 6（不在中の進行）は部屋スケール化が前提条件

## Demo 5a: 密度基準の正規化（Demo 8 の前提）

部屋スケール化（5,427セル）で箱庭（2,500セル）の2倍以上に
なったが、スポーン上限・頻度が据え置きのため密度が半減し、
「植物が少なく餓死が多い」状態になっている。これはバランス調整
ではなくスケール変更への追従漏れの修正であり、パラメータ探索は
行わない（機械的な換算のみ）。

Demo 8（情動の場化）の前に必要な理由: 個体数が少なすぎると
痕跡が減衰に負けて場が形成されず、けもの道・墓場・群れの
創発を判定できないため。

- スポーン上限・頻度をセル数に対する密度で定義し直す
- 箱庭時代の実測密度を基準に部屋スケールでの上限を逆算
- 目標: Demo 3 で観察できた程度の個体数を部屋スケールで再現

## Demo 5b: バランス探索（Demo 8 の後）

Demo 8 で恐怖場が入ると草食獣の回避行動により捕食率・生存率が
変わるため、調整は Demo 8 の後に行う。動くパラメータを全て
入れてから調整するのが順序として正しい。

- Demo 3 の実測（5070ティックで餓死1067・捕食63・出生3）と
  Demo 8 導入後の実測を比較
- CSVログ＋ヘッドレス数千ティックでパラメータ探索
- 「絶滅しない・爆発しない」範囲を回帰テスト化
- 実質は場のτと閾値の調整（層別τ設計＝ρの知見を適用）

### 場の次元の拡張点（Demo 4.5 で (d) 表面場を採用した際の持ち越し）
Demo 4.5 の場は**表面場**（各 (x,z) の最上面に付随、2D のまま）。
空間の高さ方向の層は「**フロア**」と呼ぶ（vision §7 の時間軸の
「層」＝τの速さの層と区別するため）。以下は将来の拡張点。
- **(b) フロア構造**: 面をフロアに分け、各フロアが独立した2D場を持つ。
  (d) 表面場からの移行は意味論の読み替えで可能
  （「最上面の場」→「フロア0の場」）。
- **(c) 3Dベクトル場**: アフォーダンスを個体の脳から場へ移す構想。
  個体の状態機械を薄くし、3次元に重畳した場が認知・情動の想起の
  トリガーとなる表現。移行時は**スパースチャンク方式**
  （VoxelGrid 同様の16³疎チャンク、地形表面±数セルのみ生成）を
  前提とし、実効セル数を 10^4 台に抑えて下記の PCバッチ再検討トリガ
  （10^5 セル）を回避する。
  - 3D化で場が重くなった場合の対策（優先順。着手は実測で
    決める。72FPS予算13.9ms に対する場更新の実測比率を見てから
    上から順に適用する）:
    1. スパースチャンク方式（VoxelGrid 同様の16³疎チャンク、
       地形表面±数セルのみ生成）。最も効き、他の全手法の前提
    2. アクティブセルリスト（閾値以下のセルは更新スキップ。
       植生場のような疎な場では実効セル数が1桁減る）
    3. 更新頻度の階層化（τが大きい場＝危険度場・村フィールドは
       10ティックに1回等。ρ = τ_field/τ_motion の知見と直結。
       空間的近似なしにコストを落とせる）
    4. マルチグリッド／階層的拡散（粗密2階層で解く。1〜3を
       尽くしても足りない場合の最終手段。決定論とスパース構造
       両方との整合が難しい）
    5. GPU計算（Compute Shader。ただし浮動小数点の集約順序と
       ドライバ差により横断原則2（f(シード,イベントログ)）と
       正面衝突する。採るなら「表示のみGPU、真実はCPU」の分離が必要）
  - 参考: N体問題の Barnes-Hut は本件には不適。場の更新は既に
    O(N)（局所拡散＋独立減衰）でありO(N²)が存在しないため。
    ただし動物の近傍探索が個体数増で問題化した場合は空間ハッシュ
    （Barnes-Hutではなく）で足りる

### PC バッチ更新の実施時期（2026-08 判断）
- PC バッチ更新は 2026-08 に先行検討し、**見送り**。
- 理由: 場 2,500セル / 1Hz では性能上の利得がゼロで、実機セッションに
  ネットワーク故障モードを追加するコストのみが残るため。
- 現状の詳細は docs/current_state_2026-08.md を参照。
- **再検討のトリガ（数値で判定する。議論ではなく計測で決着させる）**:
  - 場が 10^5 セル級に達した場合、または
  - tick が 10Hz を超えて Quest 単体で 72FPS を維持できなくなった場合
- 注: stigmergy_vision.md §4 は「スティグマジーのバッチ更新 = ローカルPC」と
  記述しており、設計の終着点としては維持される。本項は実施時期の判断のみを
  記録するものであり、§4 は書き換えない。

## Demo 8: 情動の場化 — アフォーダンスを個体から場へ

個体の内部状態と探索計算を段階的に場へ移す。一度に1つずつ移し、
そのたびに個体側の対応するコードが削除できることを確認する。
移すのは「情動そのもの」ではなく「情動が生む行動傾向の空間分布」。
生死・同一性・繁殖の資格は個体に残す（完全な場化は個体差を
消滅させ、繁殖・餓死が扱えなくなるため）。

- 第1段: 恐怖場＋獲物場（完了: demo-8.1.1）
- 第2段: 死の場（完了: demo-8.2.1）
- 第3段: 踏み荒らし＋進化基盤（実装・エディタ確認済み、
  実機追認待ち）— 通常表示で見えるけもの道。行動重みの
  Entity 移管（進化本体はまだ）
- 第4段: コロニー場 — 繁殖の痕跡、種ごと。群れの創発。
  この段で場が6枚になるため、進化本体（繁殖時の重み継承＋変異）
  の導入時期もここで判断する
- 第5段: VectorField 実験 — 踏み荒らし場をベクトル化し
  「ここは北へ向かう道」という方向情報を持たせる。動物が道に
  沿って移動するか。海流・風・匂いの流されへの布石
  （深海・Demo 13 の前提技術）
- 第6段: 踏み固め — 通行が地形ブロックの状態を変える
  （場ではなく構造としてのスティグマジー）。通行コスト場と統合
- 第7段: 食欲の場化（実験）— hunger の完全移管は個体差を消す
  ため、部分形（進行速度の環境依存化）を探る。移さない結論も
  ありうる

判定基準（各段共通）:
- 個体側のコードが実際に削れたか（行数と分岐の減少）
- 創発が観察されたか（けもの道 / 墓場 / 群れ）
- 決定論が保たれたか

ベクトル場・3D化はこの後。スカラー場＋勾配で表現できない情報
（循環経路、進行方向の保存、高さ方向の連続性）が必要になった
時点で判断する。

## Demo 8.5: 植物の場化 — 押し付けの本命（優先実装）

植物を Entity ではなく植生場の値そのものとして扱う。
- 摂食 = そのセルの植生場を減らす（hunger 回復は減らした量に比例）
- スポーン抽選・占有索引・表示オブジェクト管理が消え、
  エンティティ数が約200 → 数十（動物のみ）になる
- 表示は場の値から直接描く（値に応じて草の高さ3段階。
  美観は目的でなく、処理内容が確認できれば足りる。
  ちらつき対策は不要）。花は廃止し GrassTuft に統合
- 位置づけ: Demo 9 の木の実装前に「木は個体、草は場」という
  使い分けを確立する

判定基準（主軸は負荷削減）:
- M1: エンティティ数と1ティックあたり処理時間の削減を実測

  （個体数推移・餓死率・捕食率）
- M3: 決定論
- M4: 安定性（ギルド≧1、狼≧1）
- M5（記録のみ）: 草の高さで場の値が読めるか。実機
- Go条件: M1∧M2∧M3∧M4

## Demo 9: 木と果実 ＋ 水場・水分場

## 横断原則
1. 場は typed array＋スパースシリアライズ＋スキーマバージョニング
   （susuwatari-mirror 方式）で統一
2. 決定論は f(初期シード, イベントログ) として維持。
   現実由来の地形（Demo 4.5）は観測イベントとして記録し、
   同じ観測データから同じ地形が再現される形を保つ。
   M3系テストを各Demoで拡張
3. SimCore は Quest/PC 両環境で同一コードが走る設計を維持する
   （asmdef で UnityEngine 非依存を強制済み）。PC 側実行は
   2026-08 時点では見送り。再検討トリガは Demo 6 の節を参照
4. 実機テストは事前固定手順・1セッション5分以内・装着中の指示なし
