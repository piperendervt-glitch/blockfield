## 本プロジェクトの目的

生態系シミュレーションは目的ではなく実験装置である。最終的な
目的は、行動主体である個体の処理負荷を下げること（応用先:
見守り・巡回AI、フィジカルAI）。

したがって各Demoの真の評価軸は「生態系がリアルか」ではなく
「個体が持つべき状態と計算がどれだけ減ったか」である。
Demo 8 第1段で狼の視界内探索（O(N²)）が削除され、個体数に
依らない O(1) になったことが、その第一の成果。

場の追加・削除の判定基準:
- 進化的アルゴリズムで重みが0に収束した場は削除候補
- ただし重みの絶対値では判断しない（場ごとに値のレンジが違う）。
  実効寄与 = 重み × その場の勾配の典型的大きさ で比較する
- 最終判定はアブレーション（実際に削除して48シードで生存率・
  行動性能が有意に悪化しないか）
- 削除の動機は負荷削減より探索空間の縮小である可能性が高い。
  場の更新コストは個体数に依存しないため、**場化した対象が多いほど
  有利で、差は個体数とともに広がる**（場を増やした方が個体負荷は下がりうる）
  - Demo 8.5（植物の場化）の実測: 交差点は存在せず、測定した全個体数
    （11〜362）で場方式が速い。移行前は動物に加えて植物 Entity を
    100〜300体抱えるため、動物が少ない領域でも総エンティティ数では
    場方式が有利になる。差は個体数とともに広がる
    （22体で ‑16ms、362体で ‑39ms / 1000ティック）
  - ただし**場化しただけでは速くならない**。個体ループを全セル走査に
    置き換えた直後は +19% 遅くなり、ループの統合と対象セルの索引化で
    ようやく基準を下回った。場化は「個体数への依存を切る」ことであって
    「無条件に速くなる」ことではない
- 測るべき指標は「場の枚数」ではなく「1個体が1ティックで読む
  場の数」と「個体が持つ状態の数」

### レジーム論による言い直し(v10 追加)

「個体の計算を場に移す」とは、認知のレジーム間移送である:
高次元・私的・常設の内部表現(Hebb型: 特定ペア間の結合に相関を
蓄える)を、低次元・公共・訪問駆動の外部表現(場: 空間上の場所に
頻度を蓄える)に移す。

移せる量の限界は「その計算が低次元空間上の頻度統計に落とせるか」
で決まる。空間統計に落ちない計算(一回性の相関、ミリ秒の予測、
個体固有の内部状態)は内部レジームに残る。第7段の「hunger の
完全移管は個体差を消す」という予想はこの原理の適用例である。

移送の3条件(適用領域チェックリストと対): 疎な訪問で書けること、
拡散が汎化として意味を持つこと(近傍構造)、位置が読み出しを
決めること(読み手の局所性)。次元を上げるとこの3つが壊れ、
常設の重み行列+専用更新機構=ニューラルネットに変質する。
両者は同一の強化原理(使用による強化)の2つの実装レジームである。

理論的背景の詳細は docs/design/theory_notes.md を参照。

## 押し付け候補リスト（個体の計算を場へ移す候補）

1. 植物の場化（Demo 8.5）— 植物を Entity でなく植生場の値そのもの
   にする。エンティティ数が桁で減る
2. 未訪問度の場（Demo 6 と対）— 時間で増加し通過でリセット。
   個体は高い方へ動くだけで巡回が成立。巡回AIに直結
3. タスク場と予約（Demo 7）— やるべき場所に値が立ち、向かう個体が
   予約（負値）を書く。個体間通信なしの役割分担
4. 通行コスト場（踏み固めと統合）— 高低差計算を場読みに置換
5. 繁殖をコロニー場に（第4段の延長）— 隣接走査を場の閾値判定に
6. 時間管理の部分的な場化（食欲の場化で実験）— 完全な移管は
   個体差を消すため、進行速度の環境依存化など部分形を探る

## 実装済みの横断資産

以降のDemoが前提にできる、確立済みの仕組みと制約。

### 仕組み
- 決定論: f(初期シード, イベントログ)。World.Replay で
  任意のイベント列から同一 ContentHash に到達可能
  （Demo 6 の PC 側バッチが再検討される場合はこの機構をそのまま
  使える。現時点では Quest 単体で完結）
- 場（Field）: typed array 相当の float グリッド。
  植生場が拡散・減衰・書き込みで稼働中（τ小の速い層）
- 出所属性: Terrain / Player / Ecology / Reality の4値。
  TrySetBlockEcology が Player セルへの生態系側書き込みを
  API レベルで拒否（固定レイヤー原則）
- ボクセルレイキャスト: DDA（Amanatides & Woo）＋
  Predicate 遮蔽オーバーロード。エンティティと地形を
  統一的に狙える（将来の木・構造物にも適用可）
- チャンク限定再メッシュ: DirtyChunks 通知 → 該当チャンクのみ
  再生成（実測 0〜5ms）
- 表示と真実の分離: シムは 1Hz の決定論、表示は補間と仮表示。
  World の状態を表示側は決して変更しない

### 制約・知見（実機で観測済み）
- MR合成: α<1 の描画はパススルー（現実映像）と合成される。
  半透明表現は原則使わず、スケール・ワイヤーフレーム・明度で代替
- オクルージョン: 環境深度の取得だけでは不足。ARShaderOcclusion＋
  XR_HARD_OCCLUSION 対応シェーダーが必須
- HDR は無効必須（B10G11R11 はアルファを持たずパススルー合成が破綻）
- Passthrough は Android API 32 以上を要求
- 性能余裕: 8万ボクセル＠72FPS、地形生成 20ms、
  再メッシュ 0〜5ms（部屋スケール化の余地は大きい）

### 運用
- 実機テスト: 手順を事前固定し、装着中は指示・質問・生存報告を
  一切しない。ログ捕捉はスクリプト（capture_session.ps1）で行い、
  Claude Code はセッション後に一度だけ読む
- モデル使い分け: 設計判断・難所のデバッグは上位モデル、
  ビルド/デプロイ/文書記入/コミット等の定型は下位モデル

## Demo 5a: 密度基準の正規化（Demo 8 の前提）

部屋スケール化（5,427セル）で箱庭（2,500セル）の2倍以上に
なったが、スポーン上限・頻度が据え置きのため密度が半減し、
「植物が少なく餓死が多い」状態になっている。これはバランス調整
ではなくスケール変更への追従漏れの修正であり、パラメータ探索は
行わない（機械的な換算のみ）。

Demo 8（情動の場化）の前に必要な理由: 個体数が少なすぎると
痕跡が減衰に負けて場が形成されず、けもの道・墓場・群れの
創発を判定できないため。

- スポーン上限・頻度をセル数に対する密度で定義し直す
- 箱庭時代の実測密度を基準に部屋スケールでの上限を逆算
- 目標: Demo 3 で観察できた程度の個体数を部屋スケールで再現

## Demo 5b: バランス探索（Demo 8 の後）

Demo 8 で恐怖場が入ると草食獣の回避行動により捕食率・生存率が
変わるため、調整は Demo 8 の後に行う。動くパラメータを全て
入れてから調整するのが順序として正しい。

- Demo 3 の実測（5070ティックで餓死1067・捕食63・出生3）と
  Demo 8 導入後の実測を比較
- CSVログ＋ヘッドレス数千ティックでパラメータ探索
- 「絶滅しない・爆発しない」範囲を回帰テスト化
- 実質は場のτと閾値の調整（層別τ設計＝ρの知見を適用）

  （よく通る場所を動物が避ける/集まる）を観察する。

- Go条件案: 数時間の不在後の再訪で、放置領域に閉じる前と
  異なる生態が確認できる

### 場の次元の拡張点（Demo 4.5 で (d) 表面場を採用した際の持ち越し）
Demo 4.5 の場は**表面場**（各 (x,z) の最上面に付随、2D のまま）。
空間の高さ方向の層は「**フロア**」と呼ぶ（vision §7 の時間軸の
「層」＝τの速さの層と区別するため）。以下は将来の拡張点。
- **(b) フロア構造**: 面をフロアに分け、各フロアが独立した2D場を持つ。
  (d) 表面場からの移行は意味論の読み替えで可能
  （「最上面の場」→「フロア0の場」）。
- **(c) 3Dベクトル場**: アフォーダンスを個体の脳から場へ移す構想。
  個体の状態機械を薄くし、3次元に重畳した場が認知・情動の想起の
  トリガーとなる表現。移行時は**スパースチャンク方式**
  （VoxelGrid 同様の16³疎チャンク、地形表面±数セルのみ生成）を
  前提とし、実効セル数を 10^4 台に抑えて下記の PCバッチ再検討トリガ
  （10^5 セル）を回避する。
  - 3D化で場が重くなった場合の対策（優先順。着手は実測で
    決める。72FPS予算13.9ms に対する場更新の実測比率を見てから
    上から順に適用する）:
    1. スパースチャンク方式（VoxelGrid 同様の16³疎チャンク、
       地形表面±数セルのみ生成）。最も効き、他の全手法の前提
    2. アクティブセルリスト（閾値以下のセルは更新スキップ。
       植生場のような疎な場では実効セル数が1桁減る）
    3. 更新頻度の階層化（τが大きい場＝危険度場・村フィールドは
       10ティックに1回等。ρ = τ_field/τ_motion の知見と直結。
       空間的近似なしにコストを落とせる）
    4. マルチグリッド／階層的拡散（粗密2階層で解く。1〜3を
       尽くしても足りない場合の最終手段。決定論とスパース構造
       両方との整合が難しい）
    5. GPU計算（Compute Shader。ただし浮動小数点の集約順序と
       ドライバ差により横断原則2（f(シード,イベントログ)）と
       正面衝突する。採るなら「表示のみGPU、真実はCPU」の分離が必要）
  - 参考: N体問題の Barnes-Hut は本件には不適。場の更新は既に
    O(N)（局所拡散＋独立減衰）でありO(N²)が存在しないため。
    ただし動物の近傍探索が個体数増で問題化した場合は空間ハッシュ
    （Barnes-Hutではなく）で足りる

### PC バッチ更新の実施時期（2026-08 判断）
- PC バッチ更新は 2026-08 に先行検討し、**見送り**。
- 理由: 場 2,500セル / 1Hz では性能上の利得がゼロで、実機セッションに
  ネットワーク故障モードを追加するコストのみが残るため。
- 現状の詳細は docs/current_state_2026-08.md を参照。
- **再検討のトリガ（数値で判定する。議論ではなく計測で決着させる）**:

## Demo 8: 情動の場化 — アフォーダンスを個体から場へ

- 第1段: 恐怖場＋獲物場（完了: demo-8.1.1）
- 第2段: 死の場（完了: demo-8.2.1）
- 第3段: 踏み荒らし＋進化基盤（実装・エディタ確認済み、
  実機追認待ち）— 通常表示で見えるけもの道。行動重みの
  Entity 移管（EntityWeights 構造体、繁殖時のコピー継承、
  ContentHash 対象化。変異はまだ入れていない）
- 第4段: コロニー場(完了: 4a/4b/4c、Go 条件成立。M7=実機での
  群れ視認のみ帰宅後、タグ demo-8.4.1 は M7 の後)
  - 確定値: colonySelfWeight 2.4 / colonyBreedK 80 /
    colonyPresenceDeposit 0.01 / τ_colony 400 /
    群れ重みは満腹時の徘徊にのみ配線
  - 実装形態: 繁殖は閾値ゲートでなく変調型
    (breedChance × colony/(colony+k))。閾値型は双安定で不成立

  - 創発した群れは定住性コロニー(τの長い場は定住構造を作る。
    herd でなく colony。移動群は別機構 — Demo 10 参照)
  - 設計項目(実装済み): 場の結合行列。既存の2結合（死の場→植生の
    成長率、踏み荒らし場→植生の成長抑制）を FieldCoupling
    (source / target / coefficient / form) というデータに移設した。
    結合の取捨はアブレーションで行う（場は繁殖しないため進化は
    適用外。エージェント重み=進化、場の結合=探索、という分担）
- 第4.5段: 進化本体 — 繁殖時の重みに変異を導入する。
  第3段で基盤（継承・ハッシュ対象化）は完成しており、
  不足しているのは変異のみ

  第4段からの引き継ぎ:
  - 先行課題: 結合行列のアブレーション(どの結合が生きているかを
    確定してから進化に開放する。theory_notes §5.4 の前提)
  - 実験設計: 進化の初期値は群れの回廊の外(w=0 付近)から始め、
    回廊(w≈2.4)への到達を進化に課す。「進化は群れを自力で
    発見できるか」が中心の問い
  - ベースライン確定済み: 豚=羊は中立浮動(48シード、p=0.31)。
    群れのトレードオフは実在(利益=繁殖効率 / 害=過密絶滅、
    w=1.2 で餓死率が改善しながら絶滅 8/48)

  第4段の直後に置く理由:
  - 場が6〜7枚の時点なら重みベクトルの次元が追える規模である。
    Demo 9（水分場）、Demo 10（3D化）と場は増え続けるため、
    後回しにするほど探索空間が広がり観察が難しくなる
  - 実験対象が既にある。羊と豚は行動が完全に同一で中立浮動に
    より片方が絶滅する（第2段で記録）。同じ初期値から
    ニッチ分化が創発するかは進化を入れないと確かめられない
  - 本プロジェクトの目的に直結する。「重みが0に収束した場は
    削除候補」「実効寄与 = 重み × 勾配の典型的大きさで比較」
    「最終判定はアブレーション」という場の取捨選択の判定手段が
    進化そのものであり、これが動くと Demo 9 以降の場の追加判断が
    定量的になる

  コロニー場と分けて実装する理由:
  群れの形成が場によるものか進化によるものか切り分けられなく
  なるため。Demo 8.5 を独立させたのと同じ理由

  実装に必要なもの:
  - 変異: 繁殖時に親の重みへガウスノイズを加える
    （変異率・変異幅がパラメータ）
  - 決定論の維持: 変異の乱数を RNG 消費順に組み込む
  - 観察: PopulationLog の重みの平均・分散（第3段で準備済み）。
    世代を追うには数万ティックが必要なため longrun_sim.ps1 を使う
  - 判定基準: 「進化した」の定義（重みの平均が初期値から有意に
    離れる / 分散が縮む＝収束 / 種間で分岐する など）を
    事前登録で確定させる
  - 検証に環境の非定常性を含める: 適性場を一定間隔（例:
    1000ティック）で変更し（食べ物の湧く場所が移動する）、
    τがどの範囲なら追従できるかを測る。適用領域の仮説の
    成立条件(1)の検証
  - コスト構造の保護条項: 本段の進化は「生存=評価」構造により
    計算コストが下限にある(変異は繁殖時の乱数7個と加算のみ。
    選択は生態系そのものが実行し、評価関数の実行費用が存在
    しない — 評価が生活の副産物として無料で出る)。
    別の評価軸の導入(例: 特定能力の個体を意図的に選抜する)は
    この構造を壊し、評価用の追加シミュレーションが必要になる。
    導入時は必ずコスト再見積もりを行うこと
  - RL/NEAT/中央集権的ES への置換は否: コスト増に加え、中央の
    分布更新器は「場の外の神」であり個体からの計算剥奪を測る
    実験に外部の大脳を持ち込むことになる。Hebbian 可塑性
    (生涯内の局所学習)は思想と整合するが進化の置き換えでなく
    追加であり、本段完了後に Baldwin 効果の実験として検討

- 第5段: VectorField 実験 — 踏み荒らし場をベクトル化し
  「ここは北へ向かう道」という方向情報を持たせる。動物が道に
  沿って移動するか。海流・風・匂いの流されへの布石
  （深海・Demo 13 の前提技術）
  - FlowField（各セルの流下方向と上流からの積算量）を汎用の
    場操作として実装する。Demo 14 の水流侵食と押し付け候補2

- 第6段: 踏み固め — 通行が地形ブロックの状態を変える

- 第7段: 食欲の場化（実験）— hunger の完全移管は個体差を消す

  ありうる

判定基準（各段共通）:
- 個体側のコードが実際に削れたか（行数と分岐の減少）
- 創発が観察されたか（けもの道 / 墓場 / 群れ）

## 応用への展開の見通しと留保（2026-08-11 記録）

### 車輪の再発明についての自覚

本プロジェクトの機構（勾配流下、積算、フィードバック）は数学的に
確立したものであり、経路計画（ACO）、地形学（stream power law）、
最適化理論に既存の道具がある。**新しいアルゴリズムの発明ではない。**

価値があるとすればこの3点:
1. 「個体の計算をどこまで場に移せるか」の限界を実験的に測ること
2. 削除の判定を測定で行う枠組み（48シード、ContentHash、
   アブレーション）
3. 自分で回した車輪はどこで軋むかが分かるという実利

### 段階の見通し

**段階1（現在・ゲーム）の前提**: 場が中央集権的 / 全セルが確実に
読める / 時間が同期 / 環境が閉じている / 失敗コストゼロ。

**段階2（既存デジタルデータ）**: 静的グラフはほぼそのまま適用可。
時系列は空間の構築自体がモデル化になる。
次の一歩として手元のデータで1つだけ試す（候補: Git 変更履歴の場化）。

**段階3（現実世界）で同時に壊れる前提**: センサーノイズ・欠損 /
場を誰が持つか / 非同期化で決定論が失われる / 失敗にコスト。

**橋渡し実験（blockfield 上で可能）**: ノイズ注入、欠損注入、
非同期化、場の分割。「どこまで耐えるか」が実世界移行時の
センサー精度の見積もりになる。

**段階4（見守り・巡回AI）**: 既存手法（カバレッジ経路計画等）との
比較に晒される。場ベースが勝ちうるのは「通信なしの協調」
「地図を持たない」「故障時の劣化が緩やか」の3点（仮説）。

### 適用領域の仮説と3条件

スティグマジーの優位性は、**モデル化が難しい不安定要素（人間の
介入など）を、モデルを持たずに地図化できる**点にある。
試行回数を稼ぐほど地図が改善する。ただし成立条件がある:

1. 場のτが環境の変化速度と噛み合うこと
2. 変化が完全にランダムでなく構造を持つこと
3. 適応が変化を引き起こす共進化が緩やかであること

**適用の3条件チェックリスト**:
- **低知能で足りる**（場の蓄積だけで価値が出る。賢すぎる
  エージェントは場を出し抜き、地図の収束を壊す）
- **総試行量が空間サイズに対して十分**（エージェント数×訪問回数。
  多数は時間反復で代替可能）
- **近傍構造と再訪問性のある空間**

### 応用候補

**3条件が揃う（物理）**: 建物巡回・警備・清掃 / 農業圃場管理
（pico-mesh と接続） / 野生動物観測・獣害対策（trail認識AI と
接続。動物自身が書き手） / 倉庫・工場の動線 / マルチロボットの
通信レス協調 / ゴルフ（コースは不動で敵対的でなく共進化の壁が
ない。危険度場・成功痕跡場・τの階層が対応。Demo 13 のシミュ構想と
補完——シミュが物理を、場が統計を担う） / トレイルラン・登山
（ヤマレコ「みんなの足跡」は商用化されたデジタル・スティグマジー）
/ 釣り（ポイントノート文化 = 手動スティグマジーの既存運用）。

**3条件が揃う（デジタル、段階2の一歩目向き）**: コード変更履歴 /
ネットワーク障害履歴 / ゲームのプレイヤー動線（blockfield の
正当な進化形） / 文書群の閲覧動線。

**反例（限界の見極め用）**: 人流・避難誘導と スポーツの戦術読み合い
（共進化の壁。出し抜くことが本質の敵対的環境では地図が成立
しない） / 創薬・材料探索（試行が空間に対し圧倒的に疎） /
金融時系列（空間の構築がモデル化になる） / バックカントリーの
雪面（毎日の降雪が履歴をリセット。τと環境変化速度の不一致の
実例） / サーフィン（波の再訪問性が崩れる）。

**観察**: 3条件が揃う環境には**手動のスティグマジー文化が既に存在
する**（ヤーデージブック、ポイントノート、ケルン、チョーク痕）。
人間は条件が揃えば自然発生的にこの手法を運用する。デジタル化は
既存文化の増幅であり、実現可能性の傍証。
本仮説の原型は、岩場のチョーク痕・磨かれたホールドという
集合的スティグマジーへの身体的参加（クライミング）の経験にある。

### 野外での装置構成

iPhone（計算・場の管理・センシング。trail認識AI と共通基盤）＋
表示専用デバイス（USB-C 接続グラス = 計器盤方式、または骨伝導
音声）に分担する。グラス側にコードを書かないため製品依存が
生じない。世界固定表示は真の AR グラスの成熟を待つが、
スティグマジーの読み出しは低帯域で足りる（蟻は場を見ていない）
ため計器盤方式・音声1チャンネルでも機能する。

## AI・学習器の配置原理(v10 追加)

学習する AI を本プロジェクトのどこに置いてよいかの判定基準。
「決定論であること」は本質ではなく、以下の4項目が本質:

| 要件 | 判定質問 |
|---|---|
| 合算可能 | 出力はスカラー/低次元で、加算に意味があるか |
| 減衰可能 | 状態に「忘却」が自然に定義できるか |
| 局所性 | セル単位・近傍単位で閉じるか |
| 監査可能 | 人間が読んで消せるか(安全要件) |

4項目を通るなら学習器でも場レジームに使える(小さな回帰・分類器
による射影、SOM による空間構築、カルマンフィルタ/GP による
不確実性つきの場、セルごとの小さな予測器)。LLM/自己回帰生成
モデルは全項目で不適合。大きな端到端モデルを場の代わりに置くと
「読める・消せる・監査できる」が全滅し RC+AAS の安全思想に反する。

実験系全体の三層構造:
- シミュレーション内: 進化(変異+自然淘汰)のみ。学習器を入れない
- 探索層(外側): パラメータ探索が膨らんだらサロゲート(GP による
  ベイズ最適化)で試行数を削減。導入基準: 格子探索の条件数が
  20 を超えたら。シミュ内には無干渉で決定論も無傷
- 観察層(外側): 進化後の重み分布の解釈に PCA/SOM で「系統の地図」
  を作る(解析時間の削減)

この配置は「高価な内部レジームの注意配分を、安価な公共の場が
決める」という本プロジェクトの中心原理の、実験系自身への適用である。

## 横断原則
1. 場は typed array＋スパースシリアライズ＋スキーマバージョニング
   （susuwatari-mirror 方式）で統一
2. 決定論は f(初期シード, イベントログ) として維持。
   現実由来の地形（Demo 4.5）は観測イベントとして記録し、
   同じ観測データから同じ地形が再現される形を保つ。
   M3系テストを各Demoで拡張
3. SimCore は Quest/PC 両環境で同一コードが走る設計を維持する
   （asmdef で UnityEngine 非依存を強制済み）。PC 側実行は
   2026-08 時点では見送り。再検討トリガは Demo 6 の節を参照
4. 実機テストは事前固定手順・1セッション5分以内・装着中の指示なし
