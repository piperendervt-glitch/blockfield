## Demo 2: スポーンと徘徊 ＋ 場の骨格導入（優先度項目3-6）
- D0: 面方向明度差（視認性改善、Demo 1 持ち越し）
- D1: シムティック基盤（決定論。Quest/PC共用前提のAPI）
- D2: エンティティ表現（植物・動物。ContentHash対象に含める）
- D3: 適性場＋閾値スポーン — スポーン判定は最初から
  「場（typed array グリッド）からの読み出し」として実装。
  当面は静的な適性計算（Grass表層・平坦→高適性）だが、
  データ構造としての場を導入する（スティグマジーへの布石）
- D4: 徘徊AI（ランダムウォーク、高低差1昇降）
- D5: Runtime表示（動物=ブロック組合せ、移動補間）
- D6: エディタプレビュー拡張（Nティック実行）
- 捕食・繁殖は含まない

## Demo 3: 捕食・繁殖 — 場を動的にする（項目7-10）
- 植物繁殖（項目9）は植生場の拡散＋閾値スポーンとして実装
  （τ小＝速い層。個体ではなく場が繁殖の主体）
- 草食獣は植生場の勾配で草を探す（場読み行動の第1号）。
  肉食獣は視界内追跡の簡易実装で可
- 番・繁殖（項目10）は個体ベース
- 個体数時系列のCSVログ（Demo 5 の材料）
- イベントログ基盤の枠を導入（決定論を
  f(初期シード, イベントログ) に拡張）
- 視認性改善: エンティティへの面明度差適用＋地形の頂点AO
- 偵察コード: 実機セッション時に ARMeshManager から
  グローバルメッシュを取得し頂点数・バウンディングボックス・
  座標系をログ出力（Demo 4.5 の技術リスク前倒し検証）

## Demo 4: 設置・破壊 — プレイヤー干渉を場に接続（項目11-12）
- コントローラのレイキャストで設置・破壊
- ブロックに出所属性（生成地形/プレイヤー設置/生態系スポーン/
  現実由来（Demo 4.5 の Boundary を見越して））を
  導入し、固定レイヤー原則（vision §5）を構造で強制
- 設置・破壊をイベントログに記録し、場へ最小限フィードバック

## Demo 4.5: Room Terrain — 部屋が箱庭になる（新規）
- シーンモデル取得: ARMeshManager（グローバルメッシュ）＋
  ARPlaneManager（ラベル付き平面）
- 多層ハイトマップ化: XZグリッド各セルへ上から下にレイキャスト、
  複数ヒット（机上面→床面）を記録し、各ヒット面に薄い地形
  （1〜4層の起伏）を雪が積もるように載せる
- 壁の Boundary 化: 壁平面を通行不可セルとして VoxelGrid に
  ラスタライズ。既存の徘徊AIが自然に壁を避ける
- 平面ラベル→バイオーム対応: 床=平原、机上=丘陵、棚上=山岳
  （vision の「初回観測」の地形版）
- 分散生成: 生成1〜3分許容、フレーム分散
- Go条件案: 床と机の両方に地形が積もる / 動物が壁を越えない /
  机上と床で異なるバイオーム / 生成3分以内
- 配置理由: Demo 3 の生態系をジオラマで安定させてから空間を
  広げる。Demo 6（不在中の進行）は部屋スケール化が前提条件

## Demo 5: バランス調整（項目13-15）
- CSVログ＋ヘッドレス数千ティックでパラメータ探索
- 「絶滅しない・爆発しない」範囲を回帰テスト化
- 実質は場のτと閾値の調整（層別τ設計＝ρの知見を適用）
- 部屋スケールでの再調整: Demo 4.5 でセル数が増えるため、

## Demo 6: 活動場と不在中の進行 — 構想の核心（旧項目16の本体）
- 活動場: ヘッドトラッキング滞在ヒートマップ（プロキシ観測。
  カメラ画像解析はスコープ外）
- 危険度場: 放置領域で育つ（τ大）→ モンスター/巣スポーン
- PC側バッチ更新: シリアライズ→PC常駐プロセスが場を進める→
  起動時差分適用。「見ていない間に進む」の成立
- Go条件案: 数時間の不在後の再訪で、放置領域に閉じる前と
  異なる生態が確認できる

### PC バッチ更新の実施時期（2026-08 判断）
- PC バッチ更新は 2026-08 に先行検討し、**見送り**。
- 理由: 場 2,500セル / 1Hz では性能上の利得がゼロで、実機セッションに
  ネットワーク故障モードを追加するコストのみが残るため。
- 現状の詳細は docs/current_state_2026-08.md を参照。
- **再検討のトリガ（数値で判定する。議論ではなく計測で決着させる）**:
  - 場が 10^5 セル級に達した場合、または
  - tick が 10Hz を超えて Quest 単体で 72FPS を維持できなくなった場合
- 注: stigmergy_vision.md §4 は「スティグマジーのバッチ更新 = ローカルPC」と
  記述しており、設計の終着点としては維持される。本項は実施時期の判断のみを
  記録するものであり、§4 は書き換えない。

## 横断原則
1. 場は typed array＋スパースシリアライズ＋スキーマバージョニング
   （susuwatari-mirror 方式）で統一
2. 決定論は f(初期シード, イベントログ) として維持。
   現実由来の地形（Demo 4.5）は観測イベントとして記録し、
   同じ観測データから同じ地形が再現される形を保つ。
   M3系テストを各Demoで拡張
3. SimCore は Quest/PC 両環境で同一コードが走る
   （Demo 6 で初めて実際に PC 側実行が登場）
4. 実機テストは事前固定手順・1セッション5分以内・装着中の指示なし
