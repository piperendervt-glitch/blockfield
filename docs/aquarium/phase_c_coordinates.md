# Phase C: 座標系の問題（記録）

2026-08-16。系列2 Phase C で「水槽が部屋と一致しない」「クラゲが壁を抜ける」
「粒子が天井付近に無い」「HMD を被り直すとずれる」が同時に起きていた件の記録。

原因は2つあり、**どちらも描画側**だった。実機セッション5回ぶんの観測が
これに汚染されていた。

---

## 1. 根本原因: アンカーが一度も適用されていなかった

`DioramaOrigin.OriginTransform` は**実行時に** `ARAnchor` の子として作られる
`"Diorama Origin"` である。ところがシーン生成は3つの View すべてを
`anchorGo.transform` に配線していた。これは `DioramaOrigin` コンポーネントを
載せているだけの GameObject で、**原点に作られたまま一度も動かない**。

```csharp
particles.anchorSpace = anchorGo.transform;   // ← 動かない箱
jellyView.anchorSpace = anchorGo.transform;
debugView.anchorSpace = anchorGo.transform;
```

結果、粒子・クラゲ・デバッグ表示は**実質ワールド座標で描かれていた**。
焼き込み側は正しくアンカー基準（`OriginPoseAtScan`）だったので、
**力学と描画が別の座標系にいた**。

### 説明できた症状

| 症状 | 説明 | 報告回数 |
|---|---|---|
| 水槽の外接箱が部屋と一致しない | アンカーのヨー 126.9° ぶん回っていた | 2 |
| 粒子が 1.5m 付近までしか無い | アンカー高 **0.787m** ぶん下にずれ、格子上端 1.34m が天井 2.04m ではなくそこで終わっていた | 2 |
| クラゲが壁を抜ける | 力学は部屋座標で正しく、描画だけ別の場所 | 1 |
| 被り直し・リセンタでずれる | ワールド座標系は再ローカライズで動く。アンカーは実部屋に貼り付いたまま | 3 |

粒子の 1.5m は**格子の上端が 1.34m にあった**という単純な事実だった。

### 過去2回の対策は正しかった

susuwatari-mirror (2026-08-05)、blockfield VR (2026-08-13) の対策
「空間アンカー化」自体は有効だった。Aquarium シーンを新規に作る過程で
**配線を誤った**のが今回である。「新規シーンで対策が落ちた」のではなく
「対策の使い方を間違えた」。

---

## 2. もう1つの原因: 主軸ヨーを戻す回転の符号

焼き込みは `RotateAroundY(local, -yaw)` でアンカー座標を部屋座標へ移す。
描画側はその逆を掛けて戻す必要があるが、2つの回転は**符号の規約が逆**だった。

```
RotateAroundY(v, t)       : x' = x cos t - z sin t   → Unity の Ry(-t)
Quaternion.Euler(0, t, 0) : x' = x cos t + z sin t   → Unity の Ry(+t)
```

描画側は素朴に `Quaternion.Euler(0, RoomYawDegrees, 0)` と書いていたので、
戻すどころか**同じ向きに二重に掛かっていた**（2×37.8° = 75.6° のずれ）。

### 両方の修正が必要だった

配線だけ直しても 75.6° 回ったままになる。往復テスト
`RoomToAnchor_RoundTripIsIdentity` は配線とは独立に成立する性質を見ており、
旧の符号では落ちる（274件中1件失敗を確認済み）。

---

## 3. 規約化

同じ組み立てを3回書けば3回間違えられる。実際、回転の符号は**3か所すべてで**
誤っており、アンカーの配線も**3か所すべてで**誤っていた。

描画の入口を `AnchorSpaceRenderer` 1つに集約し、
`Assets/Aquarium/Scripts/` で `Graphics.DrawMesh*` を呼んで良いのは
そのファイルだけ、という grep テストを pre-push ゲートに載せた
（`AquariumRenderingConventionTests`）。

生態系の `VoxelGrid.TrySetBlockEcology`（固定レイヤー原則）と同型で、
判定が「呼んだかどうか」だけで決まり意味解析が要らないのが要点。

### 黙って壊れる形を禁じた

各 View は `m_AnchorSpace != null ? ... : Matrix4x4.identity` と書いていた。
アンカーが配線されていなくても**黙ってワールド座標で描く**という意味で、
まさにこれが今回の混入を見えなくしていた。アンカー未確定なら描かず
エラーを出す形に変えた。

**この規約テストは、書いた直後に同型の罠をもう1件検出した。**
`AquariumFlow.AnchorWorldToLocal` もアンカーが無ければ `identity` へ落ちており、
つまり**黙ってワールド座標で焼き込んでいた**。アンカーが無ければ
焼き込み自体を行わないよう直した。

---

## 4. この間に出した誤った説明

**もっともらしい説明ほど検証を省きやすい。** 以下はすべて、
筋の通った説明だったが誤っていた。

### 「粒子が天井に無いのは視線方向の奥行きの問題」

粒子の高さ分布を実機の部屋メッシュで 120 秒ぶん再現し、1.8m 帯にも 11.5% いて
時間が経っても減らないことを測った。そのうえで、目の高さ 1.5m から
半頂角 30° の円錐に入る粒子が真上 16個・水平 273個（17倍差）であることを示し、
**幾何の問題であってバグではない**と結論した。

測定自体は正しかったが、**それは「格子が正しい位置にある」前提の上での測定**
だった。実際には格子の上端が 1.34m にあり、天井付近には最初から
粒子が存在しなかった。数字が揃っているぶん、説明として強く見えた。

### 「回転の符号が原因だった」

往復テストは**変換の連鎖が誤っていた証明**としては妥当だった。
しかしそこから「実機の症状が直る」と述べたのは推論であって検証ではない。
症状には複数の原因がありえた——実際、より大きな原因が別にあった。

### 「回転の二重適用は傾きの原因ではない」

クラゲの傾きを調べたとき「ヨーだけなら水平面は水平のまま」と否定した。
**否定の論理は正しかったが、確認の範囲が狭かった。**
適用回数だけを数えて向きを確かめず、符号の誤りを見落とした。

### 共通する形

3件とも「内部で閉じた検証」で満足していた。座標系どうしの整合、
変換の連鎖、分布の測定——どれも系の内側だけを見ている。
**参照点が全部システムの内側にあると、全部が同じだけ現実からずれていても
整合は成立する。**外部の基準（パススルー越しの現実の壁）と
突き合わせるまで、この種の誤りは残る。

## 5. 検証: リセンタが起きた状態で一致していた

2026-08-16 18:15 のセッションで、修正後の挙動が確認できた。

```
18:16:17  焼き込み完了、アンカーずれ 0.0cm/0.00°
18:16:27  **リセンタを検出** 位置 127.4cm / 回転 174.43°
          (焼き込み時 (-0.091, 0.785, -0.751) → 現在 (0.152, 0.784, 0.499))
18:17:58〜18:18:03  デバッグ表示の段6→段5→段4 を確認 → すべて一致
```

**ワールド座標系が 1.27m / 174° 動いたあとで、水槽は現実の部屋に載ったままだった。**
以降セッション終了までずれは 127.3〜127.4cm で安定しており、
一度きりの再ローカライズであることも分かる。
描画停止（アンカー未確定）のエラーは0件。

意図した着脱テストは実施し忘れたが、**それより大きな座標系の移動で
検証されている**。

## 6. 有効な観測・無効な観測

この期間の実機観測のうち、

- **無効**: 描画位置に関するもの全部（水槽の位置、粒子の高さ、
  クラゲの見え方、外接箱の一致）
- **有効**: 座標系の内側で閉じているもの
  （高さ分布、固体率の内訳、平面 vs メッシュ、クラゲの拍動と遊泳速度、FPS）

固体セルの内訳（`phase_c_session.md` 付録）と、焼き込み厚が1セルである
ことの確認は有効なまま。
