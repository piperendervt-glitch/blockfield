## 構成

| 層 | 中身 |
|---|---|
| SimCore（`BlockField.SimCore.Fluid`） | `FlowGrid` / `FlowBoundaryBaker` / `CurlNoise3` / `FlowField` |
| Unity（`Assets/Aquarium/`） | `AquariumFlow` / `FlowParticleView` / `AquariumPanel` / `AquariumInput` |
| シーン | `Assets/Scenes/Aquarium.unity`（voxel terrain・植生・生態系を外し、アンカーとシーンメッシュ取得を残す） |

- **u = ∇×ψ。** 圧力ポアソンを解かないので非圧縮性が構造的に保証される
- **ψ を毎フレーム作り直さない。** 実測で ψ の構築が全体の 98% を占め、
  ∇×ψ は 48³ でも 0.28 ms（72FPS 予算の 1.9%）だった。
  重いのは解像度ではなく「毎フレーム作り直す」ことだったので、
  ノイズ項を8本の縞に分けて更新する
- **フレームでなく固定ティック（20Hz）で進める。** 縞の更新をフレーム駆動に
  するとフレームレート依存になり決定論が壊れる
- **境界は量子化して持つ。** 固体マスクと距離場（byte、1/32 セル単位）。
  距離場は整数チャンファーで作るので、**リプレイ経路に浮動小数点の
  幾何演算が入らない**（浮動小数点が要るのは「三角形→固体マスク」だけで、
  これは観測時に1回走り結果が記録される）

## 見つかった問題（5件）

すべて実機で初めて分かった。ヘッドレスのテストは全部通っていた。

### 1. 流速に物理スケールが無かった（最も大きい）

**症状**: 粒子が速すぎて流れに見えない。家具の周りに留まらないので回り込みも
見えない。自分の移動も相対的に感じられない。**3症状が同じ原因**だった。

**原因**: ψ の振幅に物理単位を与えていなかった。流速は生の ∇×ψ
（中央 2.4、単位は ψ/m）のままで、View がさらに 6〜9 倍していた。

| | 実測 |
|---|---|
| 粒子速度（中央） | **14.5 m/s** |
| 1フレーム移動（72FPS） | **20.1 cm** |
| 粒子の直径 | 1.0〜2.2 cm |

**毎フレーム自分の直径の10〜20個ぶん飛んでいた。** 仮現運動が成立する限界を
超えており、目が連続した軌跡として結べない。水中微粒子の目安
0.01〜0.05 m/s の約300〜1,400倍。

**対処**: 目標流速 (m/s) を指定し、水セルの流速の**中央値**がその値になるよう
正規化する。正規化係数は `RebuildAll` で実測から決める
（fbm の勾配統計を解析式で出すより正確で、セルサイズや渦の大きさを変えても
自動で追従する）。ノイズ座標もセル添字からワールド座標に変えた。

**採用値: 0.08 m/s**（1フレーム 0.11cm、粒子径の約1/10）。
実機で 0.02 / 0.08 / 0.3 を切り替えて 0.08 に決めた。

### 2. 境界ランプの当て方が誤っていた（独立した第2の原因）

**症状**: 家具の周りで流れが回り込まない。

**原因**: `ψ' = ψ × smoothstep(d / 2.5)` の d に**セル中心からの距離**を
入れていた。距離場が 0 になるのは固体セルなので、壁に接する最初の水セルは
d = 1.0 セル。係数は smoothstep(0.4) = **0.35** で、ψ が3分の1しか落ちていない。

| 指標 | 修正前 | 修正後 | 理想 | 無相関なら |
|---|---:|---:|---:|---:|
| \|u·n\| / \|u\| 平均 | **0.227** | **0.14** | 0 | 0.5 |
| 壁際 / 開けた所 の流速比 | **0.988** | **0.67** | ≪1 | 1.0 |

**対処**: 壁面（水セル中心から 0.5 セル）を基準にした
（`smoothstep((d − 0.5) / ramp)`）。

ランプ幅も掃引した。広げるほど接線性は上がるが、**壁際の流れが死んで
回り込みが見えなくなる**（幅5で接線性 0.099、流速比 0.21）。
2.5 セルはその折り合い。

なお 0.14 が 0 にならないのは、障害物がボクセル化された階段状の面で、
測定に使う軸平行の法線とランプが見ている面の法線が一致しないため。

### 3. View に `SpeedGain` が残っていた

正規化する前、生の ∇×ψ を見えるようにするため粒子速度を 6〜9 倍していた。
正規化後にこれが残ると、**目標流速 0.08 m/s を指定しても粒子は 0.48 m/s で
動く** — 目標値が意味を失う。削除した。

あわせて粒子の寿命を 1〜5秒 → 20〜60秒 にした。流速を 1/180 にしたので、
短い寿命のままだと**湧き直しのチラつきが動きより目立つ**
（3000粒子で毎フレーム14個が消えて現れる計算）。

### 4. 粒子マテリアルがオクルージョン非対応だった

**症状**: 家具の向こう側の粒子が手前に重なって見える。

**原因**: `GetOrCreateMaterial("FlowParticle", …, "Universal Render Pipeline/Unlit")`。
`BlockFieldOcclusionUnlit`（XR_HARD_OCCLUSION 対応）ではなかった。

**「環境深度の取得だけでは不足。ARShaderOcclusion ＋ XR_HARD_OCCLUSION 対応
シェーダーが必須」は Demo 0 で確立済みの知見**だったのに、新しいマテリアルで
踏み外した。地形・エンティティは全部オクルージョンシェーダーを使っており、
粒子だけが外れていた。

**この1件が回り込みの判定を止めていた。** 遮蔽されない状態では家具の手前と
向こうの流れが重なり、沿う構造が見えない。修正した瞬間に
「回り込んで見える」が成立した。接線性 0.14 は知覚に届いている。

既存の `.mat` は `GetOrCreateMaterial` が再利用してしまうので、
削除して作り直す必要があった。

### 5. テストが弱すぎた

`Boundary_FlowGoesAroundAnObstacleInTheMiddle` という名前で、
**測っていたのは「塊の外に流れがある」だけ**だった。「回り込んでいる」は
一切見ていない。実機で回り込みが見えず |u·n|/|u| = 0.227 だったときも、
このテストは通っていた。

**名前が主張と一致しないテストは、通ることで安心を生むぶん有害である。**

対処:
- `Boundary_FlowExistsOutsideTheObstacleAndIsZeroInside` に改名（**削除しない**
  — 流れが全部ゼロなら接線性の判定が自明に通るので、この判定も必要）
- 接線性（|u·n|/|u| < 0.20）、境界での減速（比 < 0.85 かつ > 0.05）、
  目標流速との一致、セルサイズ非依存、渦スケールの m 指定 を追加

## セルサイズの確定: 8cm

実機で「セルサイズの差が分からない」となった。**正規化が正しく効いた証拠**
であることを確認した。同じ部屋・同じ障害物・同じ目標流速 0.08 m/s で比較:

| セル | セル数 | p10 | **p50** | p90 | 渦の反転距離 |
|---|---:|---:|---:|---:|---:|
| 8.0cm | 75,712 | 0.0347 | **0.0800** | 0.1373 | 88 cm |
| 6.5cm | 139,264 | 0.0363 | **0.0800** | 0.1341 | 117 cm |
| 5.5cm | 233,700 | 0.0374 | **0.0800** | 0.1330 | 99 cm |

**中央値は3種とも厳密に一致、p90 の差は 3%。** p10 の差 8% は、粗い格子ほど
低速部の差分に打ち切り誤差が乗るため。渦の反転距離は標本が少なく（55点）
ばらつくが同じ桁。

つまり**同じ流れ場を違う解像度で標本化しているだけ**であり、
実機で差が見えないのは正しい振る舞いである。

実機の計測（3回目のセッション）:

| セル | セル数 | 焼き込み | ティック |
|---|---:|---:|---:|
| 8.0cm | 75,712 | 69ms | **4.41ms** |
| 6.5cm | 137,088 | 84ms | 8.05ms |
| 5.5cm | 222,000 | 185ms | 13.32ms |

**8cm を既定に採用する。** ティック時間が最も軽く（4.41ms、72FPS 予算 13.9ms の
32%）、格子の膨らみ問題も相対的に小さい。

## jelly_2 への申し送り: 流速とクラゲの推力の比

**0.08 m/s は「流れを見せる」には良いが、クラゲを入れるなら 0.03 m/s 程度が
良いかもしれない。**

クラゲの遊泳速度は jelly_1 段1の噴流モデルから決まる。流れが速すぎると
**流されるだけになって自力遊泳が見えない**。要るのは
「**流されている**」のか「**泳いでいる**」のかが見分けられる比である。

実際の比はクラゲの推力が出てから決める。jelly_2 の設計事項として登録すること。

## 残っている課題

- **格子の膨らみ**: 格子をアンカーの軸に合わせているため、アンカーのヨー角
  （実測 rotY=127°）で部屋が斜めに入り、軸平行の箱が膨らむ。
  実測 3.19×2.07×2.58m の部屋に対し 3.96×2.08×3.99m の格子。
  水平面積で約1.8倍。主軸合わせで解消する
- **粒子の明度がバッチ単位**: `DrawMeshInstanced` では
  `MaterialPropertyBlock` がバッチ全体に効くので、粒子ごとに明度を変えられない。
  現状はバッチ内で平均を使っている。速度帯でバッチを割る手はある
- **ティック時間の増大**: 未装着時に 4.5ms → 14ms へ増えるのを観測した。
  装着中は 4.4〜13ms で安定しており、省電力状態の影響と見ている。
  未装着時の数値は当てにならない（FPS も 61〜80 に振れる）
