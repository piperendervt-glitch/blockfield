# jelly_2 事前登録メトリクス

起草: 2026-08-16（実装前）

jelly_1（タグ `jelly-1.1`）が**機構の検証**で止まっているのに対し、
jelly_2 は **環境との結合**を扱う。jelly_1 の prereg §2 で
「J4（水槽統合）は jelly_2 に分離する」と宣言した当のものである。

---

## 1. なぜ jelly_1 に追記しないのか

Phase C の実機で「クラゲが壁に張り付いて動かない」が確認され、
その解として「壁を刺激としてクラゲの神経に入れれば、既存の機構だけで
壁を避けるはず」という筋が出た。機構はたしかに jelly_1 にある
（M-J3b: 側方刺激で進路が偏向し、刺激が消えると復帰。実測 360.0° → 315.1° → 復帰）。

しかし**環境がモデルの中で神経に結合する**ことは、jelly_1 が明示的に
切り出した範囲である:

- §2「J4（水槽統合）は jelly_2 に分離する」
- §5.2「環境・餌・繁殖は jelly_2」
- §6.1「機構の検証であって適応の測定ではない。後者は jelly_2 の領分」

追記で済ませると、**分離を宣言した当のものを戻す**ことになり、
prereg の境界が意味を失う。jelly_2 として立てる。

## 3. K3: 境界からの侵害受容（中核）

### 3.1 何を入れるか

壁に最も近いリングセルへ刺激を入れる。逃避の向きは
**既存の機構（M-J2b: 伝播の時間差 + 減衰勾配）から創発させる**。
新しい操舵則は書かない。

| 決めること | 登録値 | 根拠 |
|---|---|---|
| どのセルに | 壁に最も近い1セル | 実物の侵害受容器は体表に固定され、どれが発火するかは接触が決める |
| どの強さで | `ExcitableParams.ExcitedLevel` と同じ（通常の刺激と同格） | 強さを別に持つと自由度が増え、創発の主張が弱まる |
| いつ | 壁面距離が **傘半径 + 1セル** を下回っている間、**拍動周期 T ごとに1回** | 毎ステップ入れると不応期で半分が空振りし、T = R₀ の谷と同じ現象が起きる（§5.2） |

### 3.2 主張

> **環境が刺激の位置を決め、逃避の向きは依然として創発する。**

これは M-J2b（動物が行き先を決めるのに方向を計算していない）から
**自動的には従わない新しい主張**である。「壁に最も近いセル」を求めるのは
方向の計算だからである。

**分界**: その計算は**環境の側**（`JellyBoundary`）に置く。
動物の内部状態からは方向を作らない。

### 3.3 固定の仕方

| 固定 | 方法 |
|---|---|
| 神経側に方向計算が入らない | grep テストの走査対象は `SimCore/Excitable` + `Fluid/Jellyfish.cs` のまま。**`JellyBoundary.cs` は対象外**（環境の情報を扱う層） |
| 刺激の位置が環境由来であること | 壁の配置を変えたら刺激セルが変わることをテストで固定 |
| 逃避の向きが創発であること | 同じ刺激セルに対し、g を変えると向きが反転する（M-J2b の符号反転境界が生きている）ことを再確認 |

### 3.4 判定（**実行前に決める**）

| ID | 判定 | 合格条件 |
|---|---|---|
| **M-K3a** | 壁への接近が減る | 止水・同一シードで、侵害受容ONのほうが**壁面距離の時間平均が大きい**。48シードでの符号一貫 ≥ 40/48 |
| **M-K3b** | 静止しない | 侵害受容ONで、**実移動速度の時間平均が遊泳目標の 50% 以上**を保つ（OFF では 0 に落ちる） |
| **M-K3c** | 部屋を使う | 訪れた格子セルの数（被覆）が OFF より多い。48シードでの符号一貫 ≥ 40/48 |

**M-K3b が要である。** Phase C で「泳げている」と報告する指標
（推力からの積分）が「止まっている」個体に出ていたので、
**実移動で測る**ことを判定に明記する。

### 3.5 予想（先に書く）

**往復に落ち着くと予想する。**

M-J3b は「刺激が消えると**元の進路に復帰する**」である。壁から逃げれば
刺激が消え、ペースメーカーが元の向きへ戻すので、壁へ戻ってまた逃げる。
持続的な進路変更にはならない。

したがって:

- **M-K3a・M-K3b は合格する見込み**（張り付きは解消する）
- **M-K3c は不合格または僅差の見込み**（部屋を泳ぎ回るところまでは行かない）

**この予想が当たった場合、それは失敗ではない。** 持続的な進路変更には
**体の向きが状態として残る**ことが要り、それが K2 の傘の軸である。
K3 を K2 の後に置いているのはこのためで、K3 単独では往復までが上限、
という理解を先に登録しておく。

**予想が外れて M-K3c が合格した場合**は、その機構（なぜ復帰しないのか）を
記録すること。M-J3b の復帰性と矛盾するので、どちらかの理解が誤っている。

## 4. K4: 2×2 要因計画

`flow_colony.py` の測定から置き換えた仮説をそのまま登録する。

> **剛性は群体成立の前提条件であり、流れは剛性がある場合にのみ利益に転じる。**

| 条件 | プロトタイプ実測 |
|---|---|
| flexible + 流れ | 0.183 |
| rigid + 流れ | **0.270** |
| rigid + 静水 | 0.218 |

**2×2 要因計画（flow × rigid）、48シード。**
交互作用の符号が上の並びと一致するかを見る。

**検定台の限界を併記する**（`docs/prototypes/README.md`）:
プロトタイプはビューア版の「link が 0.03 まで刈られる」現象を再現して
おらず、**検定台そのものが未検証**である。M-F2 の逆向きの結果は
「流れ仮説の反証」としては読めない。

### 4.1 遺伝子化

jelly_1 §5.2 の規約を引き継ぐ。

- 受容器から運動への接続は**速度（θ）と旋回率の2経路を独立に持つ**。
  片方だけの実装を禁止する
- **旋回率への結合係数は手で置かず、遺伝子とする**

根拠（M-K1、`homeostat.html`）: 用量反応は単調（係数
0 / .006 / .012 / .024 / .048 / .096 に対し 0.492 / 0.510 / 0.512 /
0.553 / 0.586 / 0.664）だが、**生存には最適値がある**
（0.024 を超えると 42.0 → 39.7 → 38.8 → 31.7）。値を固定すると
「世界定数の設計」ではなく「個体の戦略パラメータの調整」になり、
創発の主張が無効になる。

## 5. 探索空間の境界（jelly_1 からの申し送り）

遺伝子探索を始める前に、**既知の落とし穴を境界として登録しておく**。

### 5.1 限定1: 重ね合わせは密な刺激では線形でない

M-J2d（ベクトル平均）は**2点・90°離れの範囲でのみ**成立する。
0°・90°・180° の3点同時刺激では:

| | 値 |
|---|---|
| ベクトル平均の予測 | 270° |
| 実測 | **90°（正反対）** |
| 移動距離 | 0.775（単一刺激 11.921 の 6.5%） |

各セルは不応期のあいだ1度しか発火できないので、重なった波は
足し算にならない。**侵害受容が複数の壁から同時に入る状況（部屋の隅）は
この領域に入る。** 隅で逃避が破綻することを想定しておくこと。

### 5.2 観察A: T = R₀ の谷

拍動周期 T を遺伝子にするなら、探索空間はこうなっている。

| T | 刺激が入った | **波が出た** | 平均速度 |
|---:|---|---|---:|
| 15 (= R₀+1) | 107/107 | 107/107 | **0.792（最速）** |
| **14 (= R₀)** | **115/115** | **58/115** | **0.428（谷）** |
| 13 | 62/124 | 62/124 | 0.462 |

- 上限側: 制約なし（遅いだけ）
- **最速は T = R₀ + 1**
- **T = R₀ ちょうどは谷**（両隣より遅い）。**勾配法だと嵌まりうる**
- T < R₀ は実効的に 2T に折り返す（探索が無駄になる領域）

**「刺激が入った」と「波が出た」は別物である。** 受理数だけを数えると
この谷は見えない。同じ理由で、侵害受容も**入れた回数ではなく
波が出た回数**で記録すること。

## 6. 水槽側の申し送り（Phase C から）

| 項目 | 値 | 出所 |
|---|---|---|
| 目標流速 | **0.03 m/s**（既定） | 遊泳 0.04 m/s に対し、0.08 では流れが2倍速くほぼ流されるだけになる |
| 遊泳速度 | **0.04 m/s** | 実測で目標比 1.000 |
| 傘径 | 15cm（既定） | 拍動が知覚に届く。変形量の誇張は不要だった |
| 拍動周期 | 1.0 秒（神経 40Hz × 40 ステップ） | 流れ場 20Hz と整数比 2:1 |
| 壁の反発 | **無効（0.00）** | 旋回が無い状態では釣り合うだけ。K2 の後に見直す |

**流速と遊泳速度の比が 1 付近であること**が、「流されている」のか
「泳いでいる」のかを見分けられる条件である。判定には
**止水モード（流速 0.00）**を使う。流れがある状態で目視判別するのは
原理的に難しい（周囲との相対速度が見えないため）。

## 追記1: K1（抗力係数の逆算）の手順（2026-08-16、計測前に登録）

### A1.1 なぜソース定数を読むだけでは駄目か

`jelly_side.html` の体の力学は毎ティックこの形をしている。

```js
bell.vx += dux*J;                       // 噴流の推力
bell.vx += Fx*0.9*CS/M;                 // 浸漬境界の反作用
bell.vx *= 0.985;  bell.om *= 0.95;     // 抗力（1次減衰）
```

`0.985` をそのまま持ってくることもできるが、**それは有効な抗力ではない**。
浸漬境界の反作用 `Fx` も速度に依存するので、実際の減速は 0.985 だけでは
決まらない。減衰係数だけを読むのは「理論値を使わない」の趣旨を外す。

**走らせて測る。**

### A1.2 計測手順（区間・除外を先に固定する）

| ID | 測るもの | 手順 |
|---|---|---|
| **M-K1a** | 並進の抗力 τ_trans | ペースメーカー停止・流体静定後に `vx = v0` を与えて惰行。**\|v\| が 0.8·v0 → 0.2·v0 の区間**で `ln\|v\|` を直線当てはめ |
| **M-K1b** | 回転の抗力 τ_rot | 同じ手順を `om = ω0` で |
| **M-K1c** | 推力 | ペースメーカーONで定常後、**5拍動（1150ティック）を捨ててから5拍動**の平均速度 |

当てはめ区間を先に決めるのは、**範囲を後から選べないようにするため**である。

### A1.3 不合格条件

**当てはめの R² < 0.98 なら K1 を保留する。**

「1次減衰」というモデル自体が合っていないことになるので、
**単一の係数に押し込めてはいけない**。その場合は抗力の形から見直す。

### A1.4 単位のアンカー

px/ティック → m/s の換算に2つ要る。**どちらもモデルが与えるもので、
選ぶ余地がない。**

- **時間**: `t%230===10` で拍動 → **1拍動 = 230ティック ≡ 1.0 秒**
  （こちらの `PulsePeriodTicks / 40Hz`）。⇒ 1ティック = 1/230 秒
- **長さ**: 傘の直径 `2·Rb` px ≡ `BellDiameter` = 0.15 m

### A1.5 ビューポートを固定する（後から選べる自由度）

```js
const Rb = Math.min(W*0.30, 150);
```

**傘の大きさがビューポート幅で変わる。** スマホ（W≈390）で 117px、
デスクトップ（W≈1200）で 150px（頭打ち）。流体格子は `CS=6` 固定なので、
**傘が格子何個ぶんかが画面によって変わり、流体の効き方も変わる。**

- **登録するビューポート: W=390, H=844**
  （プロトタイプは `maximum-scale=1`・safe-area 対応のスマホ前提）
- **併せて W=1200, H=800 でも測り、無次元比 τ_rot/τ_trans が
  両者で一致するかを見る**

比が一致すれば抽出は頑健。**食い違えばそれ自体が知見**で、
ビューポートを固定した旨を明記して進む。
判定を後から作らないよう、この頑健性チェックも手順に含める。

### A1.6 主たる成果物

C# へ持ち込むのは**無次元比 τ_rot/τ_trans を第一**とする。
px もティックも消えるので、換算アンカーの誤りに影響されない。
τ_trans 自体は時間アンカー経由で秒に直す。

### A1.7 参考値（**合わせにいかないために先に書く**）

ソース定数から素朴に計算すると:

| 量 | 素朴な計算 | 現行の C# |
|---|---|---|
| τ_trans | -(1/230)/ln(0.985) ≈ **0.29 秒** | `Drag=0.1 @40Hz` → 0.24 秒 |
| τ_rot | -(1/230)/ln(0.95) ≈ **0.085 秒** | 未実装 |
| τ_rot / τ_trans | **≈ 0.30**（回転の抗力が並進の約 3.4 倍） | — |

**これは実測ではない。** 反作用を含んだ実効値は A1.2 の手順で測る。
この数字を知ったうえで測ると無意識にそこへ寄せる力が働くので、
**自覚して先に明記しておく**。実測がこの値から離れても、
手順どおりなら実測を採る。

### A1.8 ハーネスの検証（本計測の前）

物理は 240 行中の 50〜186 行に閉じており、DOM に触れているのは
canvas 設定・入力・描画だけなので、node へ切り出して無描画で回せる。

**本計測に入る前に、ハーネスがプロトタイプと同じ振る舞いを出すことを
確認する**:

- 拍動周期が 230 ティックであること
- ペースメーカーONでの定常速度が得られること（発散も停止もしない）

## 追記2: K1 の計測結果 — **M-K1a / M-K1b 不合格。K1 を保留する**（2026-08-16）

### A2.1 ハーネスの確認（A1.8）は通った

| 確認 | 結果 |
|---|---|
| 拍動周期 | **ちょうど 230 ティック**（5周期とも） |
| 定常遊泳 | 得られる。発散も停止もしない |

確認スクリプト自体のバグを2件直してから通した。
1件目は**空振りの合格**（拍動を0件しか検出できていないのに
`[].every()` が true を返して「OK」と表示していた）。
2件目は `reset()` が `world.pace` を戻しておらず、前の計測で切った
ペースメーカーが次へ漏れていた。

### A2.2 M-K1a / M-K1b: **登録した当てはめ区間で標本が取れない**

惰行させると、速度は減衰しない。**振動する。**

登録ビューポート（W=390）で `v0` を与えた直後の `v/v0`:

```
並進  0:1.558  1:0.375  2:0.952  3:0.025
回転  0:2.453  1:1.892  2:2.144  3:1.732  4:1.764  5:1.492 …
```

頑健性チェック（W=1200）はさらに極端で、**注入値の 42 倍へ跳ね上がり、
以後 12〜57 のあいだをティックごとに往復し続ける**:

```
並進  0:42.345  1:22.359  2:41.088  3:11.755  4:48.983  5:11.621  6:56.833 …
```

`|v|` が 0.8·v0 → 0.2·v0 を単調に通過しないので、**A1.2 で登録した
当てはめ区間そのものが取れない**。R² を計算する手前で止まっている。

### A2.3 判定: 保留（A1.3 のとおり）

A1.3 は「R² < 0.98 なら 1次減衰というモデル自体が合っていないので、
**単一の係数に押し込めてはいけない**」と登録していた。
実際には R² を出すまでもなく、応答が単調ですらない。**保留する。**

**参考値（τ_rot/τ_trans ≈ 0.30）へは寄せない。** A1.7 で
「実測がこの値から離れても手順どおりなら実測を採る」と宣言している。
いま採るべき実測が無いので、値を出さない。

### A2.4 機構の見立て（未検証）

浸漬境界の直接強制は、体の速度と流体の速度の差に比例した力を
双方に与える。**体と流体が2自由度の連成振動子になっている**と見られる。
ティックごとに符号が入れ替わる往復（周期2の振動）は、
その連成が数値的に不安定な領域に入った形と整合する。

もう1つの可能性として、**注入の仕方がプロトタイプの通常の動作域から
外れている**ことも考えられる。通常の遊泳では境界速度は筋収縮の形状変化が
作るもので、剛体の並進ではない。剛体を丸ごと動かす摂動は、
直接強制の枠組みが想定していない入力かもしれない。

**どちらが主因かは未検証。** 断定しない。

### A2.5 M-K1c（推力・定常遊泳）は測れた

### A2.6 頑健性チェックの結果: **ビューポート依存が大きい**

A1.5 で「食い違えばそれ自体が知見」と登録していた。**食い違った。**

### A2.7 次の一手（提案。承認を得てから実施）

惰行による抽出をやめ、**動作域の中で測る**形に変える。

定常遊泳では、1拍動あたりの推力積分と1拍動あたりに抗力へ失われる
運動量が釣り合っている。両方ともプロトタイプの内部量として取れる:

- 1拍動あたりの推力積分（`J` の総和）
- 同じ区間の平均速度（M-K1c で測れている）

ここから**動作点における実効抗力**が出る。摂動を与えないので、
A2.4 の「通常の動作域から外れる」懸念を回避できる。

**ただしこれは登録した手順の変更である。** 結果を見てから手順を
変えた形になるので、変更後の手順を先に登録し、
**A2.2 の生データは差し替えずに残す**。

### A4.2 診断: 「惰行区間」は惰行していない

登録した +60〜+200 ティックは、推力が出ていないという意味では正しい。
しかし**そこで速度は減っていない。増えている**（0.16 → 0.30）。
k > 1、単調率は 50% 前後で、指数減衰どころか**方向性のない揺らぎ**である。

原因は数字に出ている。**1拍動あたりの推力積分は 7.36 px/tick、
定常の平均速度は 0.114 px/tick。** 推力は実際の速さの 65 倍ある。

つまり噴流の推力は**ほぼ全部が浸漬境界の反作用で打ち消されている**。
体の運動は、**大きな2項がほぼ相殺した残差**として決まっている。

### A4.3 結論: この系は「推力 − 抗力·v」ではない

追記2 では「1次減衰かどうか」を疑っていたが、そこが問題ではない。
**抗力という分離した項が存在しない。** 流体を介した2つの大きな力の
相殺で運動が決まっているので、`k·v` の形に要約できない。

条件2（k の安定性）だけが合格しているのは示唆的で、
**k ≈ 1.000 が5拍動とも安定して出ている** = 「惰行区間では速度が
だいたい保たれる」ことは再現性がある。減衰が測れないのであって、
測定が不安定なのではない。

### A4.4 K1 を「係数の逆算」として続けない（提案）

prereg §2 は K1 を「抗力係数の逆算」と書いたが、
**このプロトタイプから抗力係数は取り出せない**というのが2回の計測の結論である。
手順を3度変えれば取れる、という見込みは持っていない。

**K2 が実際に必要とするものは係数ではない**ことに注意したい。
C# 側は既に遊泳速度を実測で正規化している（`Jellyfish.SpeedScale`）。
K2（dV/dt と旋回）に足りないのは、**旋回の強さを遊泳と結びつける
無次元量**である。

これはプロトタイプから**振る舞いとして**取れる:

- 片側だけ発火させたときの **1拍動あたりの回頭角**
- 同じ条件での **1拍動あたりの前進距離**
- 比 = **体長あたりの回頭角**（px もティックも消える）

係数を経由せず、必要な量を直接測る形になる。
プロトタイプを**係数の供給源ではなく振る舞いの供給源**として使う。

**これは K1 の定義変更なので、実施前に承認を得る。**
承認された場合は追記5 として手順と不合格条件を先に登録し、
追記2・追記4 の生データは残す。
