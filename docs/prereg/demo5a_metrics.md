## スコープ
- SimParams のスポーン上限・頻度を「セル数あたりの密度」で定義
- 箱庭（2,500セル）時代の実測密度を基準に部屋スケールへ換算
- 適性セル数（suitability > 0 のセル）を基準にするか、
  総セル数を基準にするかは実装時に判断し理由を記録

## メトリクス
- M1（密度の回復）: 部屋スケールで、視界内に常時植物が見え、
  動物が複数頭確認できる。実機で目視
- M2（餓死の減少）: パネルの餓死累計の増加ペースが
  Demo 4.5 セッション時より明確に緩やかになる
- M3（決定論の維持）: 同一シード＋同一ティック数で
  ContentHash 一致。EditModeテスト
- M4（性能・記録のみ）: 個体数増加後も72FPS維持

## Go/No-Go

- No-Go時: 原因を1行メモしてから対処（基準は変更しない）

## 追記（2026-08-09: 実装の判断と実測値）

判定基準は変更していない。実装時の判断と、換算前後のヘッドレス実測を記録する。

### 基準セル数は「適性セル数」を採用
壁・天井・穴のセルを分母に入れると、同じ広さの部屋でも家具や間取りで密度が
ぶれる。適性セル（suitability > 0）は実際にスポーンが起こりうる場所そのもの
なので「1セルあたり何個体」という意味がそのまま通る。
実測でも適性率は箱庭89.0% / 部屋94.6% と差があり、総セル基準ではこの差が
そのまま密度の誤差になる。

基準値は箱庭 50x50（seed=12345）の適性 **2,225セル**。既定値をこのスケールでの
絶対数として持ち、`SimParams.Resolve(適性セル数)` が比例換算する。
換算は整数演算のみ（浮動小数点を挟まない）なので決定論は環境に依らない。

### スポーン頻度も換算対象にした
抽選候補数を据え置くと、セル数が増えたぶんだけ1ティックあたりのカバー率が
下がり、立ち上がりが遅くなる。実測でカバー率は箱庭0.45% / 部屋0.18% と
半分以下になっていた。換算後は両者とも0.45%で揃う。

### 実測（3,000ティック、ヘッドレス）

| | 箱庭 2,225適性 | 部屋 5,135適性（換算前） | 部屋（換算後） |
|---|---|---|---|
| plantCap | 200 | 200 | **461** |
| animalCap / SpawnCap / wolfCap | 30 / 20 / 4 | 30 / 20 / 4 | **69 / 46 / 9** |
| 抽選候補 植物 / 動物 | 10 / 2 | 10 / 2 | **23 / 4** |
| 抽選カバー率/tick | 0.45% | 0.18% | **0.45%** |
| 定常 植物 / 動物 | 199.2 / 29.1 | 199.5 / 19.9 | **459.9 / 61.3** |
| **植物密度** | **89.55‰** | 38.86‰ | **89.57‰** |
| 動物密度 | 13.06‰ | 3.88‰ | 11.94‰ |
| 立ち上がり t300 (植物,動物) | (38,21) | (44,20) | **(164,46)** |
| 餓死累計 t300 / t3000 | 16 / 69 | 30 / 173 | 40 / 281 |

- **植物密度は 89.55‰ → 89.57‰ とほぼ完全に一致**。目的は達成。
- 動物密度は 11.94‰ で箱庭の 91%。捕食圧と餓死の効き方が広さで少し変わるため
  完全一致はしないが、換算前の 30% からは大きく回復した。
- 箱庭では換算後も**従来と完全に同じ値**（200/10/30/20/4/2）に解決される。
  ContentHash も個体数の推移も不変であることを確認済み。

### M2 の解釈について（基準は変更しない）
**餓死の累計は絶対数では増える**（部屋 t3000: 173 → 281）。個体数が3倍に
なったためで、**1個体あたりでは 8.7 → 4.6 とおよそ半減**している。
パネルに出るのは絶対値の累計なので、M2 を「パネルの数字が小さくなる」と
読むと不成立になる。実機判定では「植物が常に見えていて、動物が餓死で
消える前に食べ物にありつけているか」を見ることを推奨する。
なお Go 条件は M1 かつ M3 であり M2 は含まれないため、判定には影響しない。
