### M1 の判断根拠
- **動物密度 0.88% は箱庭 t300 の 0.94% とほぼ同水準**。換算前の実機セッションでは
  20頭 / 5,135適性 = 0.39% だったので**倍以上に回復**した。
  動物は tick 60 で約40頭に達して以降ほぼ横ばい（`animalSpawnCap` に張り付き）。
- 植物密度 0.88% は箱庭 t300 の 1.71% の約半分だが、これは**セッションが
  198ティックで終わったため**であり、単調増加の途中だった（10→40で頭打ちなし）。
  ヘッドレスでは部屋の t300 で **3.19%**（箱庭 t300 の 1.71% を上回る）に
  達することを確認済み。この根拠により立ち上がり途中と判断し M1 を合格とする。

### M2 について
ヘッドレス3,000ティックの実測で、餓死の**絶対数は増える**（173 → 281。
個体数が3倍になったため）が、**1個体あたりでは 8.7 → 4.6 と半減**している。
実機セッションでは摂食成功率・餓死率ともに**指標を取得できなかった**
（下記の反省を参照）。Go 条件に M2 は含まれないため判定には影響しない。

### M4（性能）
VRモードで全区間 72FPS 維持（72.0 / 72.0 / 72.0 / 71.9 / 72.0 / 71.9）。
今回追加した診断表示（密度指標・個体数グラフ・飢餓の色分け）による劣化はない。
17:23:38 の `FPS=0.3` は HMD 再装着直後の1サンプル（`APP_CMD_RESUME` 直後）で
性能問題ではない。

## 反省: 指標がログに出ていなかった
密度指標をパネルの表示テキストにしか出しておらず、30秒ごとの `Debug.Log` には
FPS・モード・ブロック数しか出していなかった。そのためセッション後に
**摂食成功率と1個体あたり餓死率を復元できなかった**（密度と個体数は
population.csv とログの適性セル数から再計算できた）。

Demo 4.5 の M6（FPS）でも同じ「パネルにしか無い数値は取得できない」漏れを
起こしている。再発防止として:
- 密度指標を30秒ごとのログに追加（本コミット）
- **「パネルに表示する指標は必ずログにも出す」を CLAUDE.md の
  実機テスト運用に規約として追記**

## 副次的な収穫: 座標系の追従を数値で確認
以前保留にしていた「メタボタン長押しでの座標系ズレ」の懸案が解消した。
セッション中に再センタリングが2回起き、アンカーのワールドポーズが大きく
動いたが、**地形ルートの local は完全に不変**でワールド座標だけが追従していた。
